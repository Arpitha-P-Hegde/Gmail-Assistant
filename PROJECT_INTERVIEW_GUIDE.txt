SMART MAIL MANAGER — COMPLETE INTERVIEW GUIDE
================================================

1. THE 60-SECOND EXPLANATION
----------------------------
Smart Mail Manager is a privacy-oriented desktop email-organising and search
application. A user authorises read-only Gmail access through OAuth 2.0. The
Python backend synchronises recent Gmail messages, parses their MIME payloads,
stores normalised records locally in SQLite, assigns each message a category,
and builds semantic vectors in a local FAISS index. The React/Electron desktop
client then lets the user browse filters, read an email, synchronise again, or
ask natural-language questions about the local mailbox.

The key design choice is that it is a local retrieval system, not a general
chatbot with mailbox access. Structured queries such as “show unread job
emails” are resolved from SQLite metadata. Semantic questions use local
all-MiniLM-L6-v2 embeddings and FAISS. FLAN-T5-small is loaded locally only
when the user asks to summarise an already retrieved email. That separation
reduces hallucination risk and keeps mail content on the user’s machine after
the one-time Gmail retrieval.

Interview pitch:
“I built a desktop Gmail assistant with a React/Electron UI and a Python
FastAPI adapter. Its pipeline is Gmail OAuth → MIME parsing → SQLite → hybrid
rule/embedding categorisation → FAISS semantic retrieval. Intent routing keeps
metadata answers deterministic, and generative AI is constrained to summaries
of retrieved source mail.”


2. WHAT THE APPLICATION DOES TODAY
----------------------------------
Implemented:

* OAuth 2.0 browser consent for Gmail’s gmail.readonly scope.
* Fetch up to 50 recent Gmail messages and parse headers, labels, MIME body,
  snippet, thread ID, and attachment presence.
* Store only new Gmail message IDs in local SQLite.
* Categorise mail as Jobs, Education, Shopping, Bank, LinkedIn, GitHub, or
  Other using deterministic rules first and embeddings otherwise.
* Build/search a FAISS semantic vector index.
* Browse Inbox, category, attachment, important, and starred views.
* Answer latest, metadata, sender, subject, semantic-search, and summary
  requests with clickable source emails.
* Summarise a retrieved email locally using FLAN-T5-small, with a deterministic
  excerpt fallback if the generated text fails quality checks.

Not implemented / incomplete:

* No send, delete, label-change, or other Gmail write operation.
* Attachments are detected, not downloaded or scanned.
* Sync is recent-message polling, not pagination, Gmail history-ID incremental
  sync, push notifications, or a background scheduler.
* There is no trained classifier, feedback loop, account system, encryption
  layer, formal migrations, telemetry, or automated test suite.
* Electron does not start/package the Python backend. The UI hard-codes
  http://127.0.0.1:8000/api, so a packaged app still needs local FastAPI.

4. ARCHITECTURE
---------------

    Gmail API (Google cloud)
             | OAuth 2.0 / HTTPS / read-only
             v
    auth.py → gmail_client.py → GmailService
             |
             v
    main.sync_emails()
       | parse MIME, headers and labels
       v
    SQLite data/mail.db  ← category update
       |                         ^
       |                         | rules + MiniLM category similarity
       +→ build_index.py → FAISS data/emails.faiss + JSON ID metadata
                                  |
    React/Electron ← HTTP/JSON ← FastAPI api.py ← rag.py/search_emails.py
                                  |
                           local MiniLM / local FLAN-T5 when needed

There are two deliberate data paths:

1. SQLite is the durable source of truth for stored records and exact metadata
   filters.
2. FAISS is a derived, rebuildable vector index for semantic queries. Its
   vector positions map to Gmail IDs through faiss_metadata.json, then to
   current SQLite rows.


5. END-TO-END FLOWS
-------------------
Authentication and sync

1. auth.get_credentials reads token.json, if present.
2. Expired credentials with a refresh token are refreshed in memory. Otherwise
   InstalledAppFlow.run_local_server(port=0) opens browser consent and writes
   token.json. OAuth delegates access; the app never sees a Gmail password.
3. GmailService lists recent IDs with userId="me" and fetches each full message.
4. ml.parser normalises each Gmail payload into a stable email dictionary.
5. save_email uses INSERT OR IGNORE and Gmail ID as the primary key, making
   repeated storage syncs idempotent.
6. categorize_emails assigns categories only to uncategorised rows.
7. UI sync passes rebuild_index=True, recreating FAISS and its JSON metadata
   from all SQLite emails.

Browse mail

Electron opens a BrowserWindow with context isolation enabled and Node
integration disabled. React calls loopback FastAPI using fetch. FastAPI
serialises SQLite data to stable frontend fields. The UI has a sidebar, list,
reader, and assistant; selecting a list row fetches the full body by ID.

Ask the inbox

1. POST /api/ask validates a 1–1000-character query.
2. rag.detect_intent applies deliberately small deterministic rules.
3. Latest answers use SQLite dates; metadata answers use SQLite labels/fields;
   semantic/sender/subject retrieval uses FAISS.
4. FAISS source matches are shown as cards with similarity scores.
5. A summary runs FLAN-T5 only on the top retrieved email, with body truncated
   to 2,500 characters; invalid generation falls back to a deterministic excerpt.


6. BACKEND MODULES
------------------
src/auth.py
  Owns scope, project-relative credential paths, saved-token loading, refresh,
  first login, and token persistence. Scope is gmail.readonly.

src/gmail_client.py and src/gmail_service.py
  Separate Gmail API construction from list/get operations. Full messages are
  retrieved with format="full". This is a thin wrapper, which is easy to mock.

src/main.py
  Orchestrates sync: initialise DB, fetch/parse/store, categorise, optionally
  rebuild FAISS, and return added/existing/fetched counts. It catches only
  TransportError during service creation; other Gmail API calls need handling.

src/ml/parser.py
  Produces id, thread_id, from, to, cc, subject, date, snippet, label_ids,
  has_attachment, and body. It lowercases headers, recursively traverses MIME,
  base64url-decodes data, converts HTML through BeautifulSoup, and treats a
  filename in any part as an attachment. It returns the first non-empty text
  part; it does not download attachments.

src/ml/cleaner.py
  Strips HTML and replaces URLs, email addresses, phones, and money values
  with semantic markers; also normalises subjects and sender parts. It is
  currently an available utility, not used by the active embedding pipeline,
  which stores raw parsed body_text.

src/database/db.py
  Creates data/mail.db and emails table, compatibly adds category to older DBs,
  and creates thread/category indexes. sqlite3.Row provides dictionary access.

src/database/email_repository.py
  Provides INSERT OR IGNORE persistence, lookup by ID, thread/category lookup,
  category update, and correctly parsed date ordering for latest email.

src/categorize_emails.py
  Uses high-confidence sender/keyword rules first. Otherwise it embeds
  “Subject + body”, compares it to embeddings of category descriptions, and
  selects the largest normalised dot product (cosine similarity).

src/ml/embeddings.py and src/ml/build_index.py
  Load all-MiniLM-L6-v2 in offline-only mode, create normalised message vectors,
  add them to faiss.IndexFlatIP, and persist binary index plus aligned metadata.

src/search_emails.py
  Applies structured filters to SQLite rows. No text query means metadata-only,
  newest-first search; a text query searches all FAISS vectors then applies the
  allowed-ID filter, avoiding a false empty result when top vector hits fail a
  metadata condition.

src/rag.py
  Routes intent and formats retrieved answers. “RAG” is intentionally narrow:
  nearly all responses are deterministic retrieval; generation only summarises
  a selected retrieved email.

src/api.py
  Is the local REST boundary. Lifespan initialises SQLite; Pydantic validates
  asks; serializers translate DB fields to UI shape; endpoints map failures to
  404, 409, 503, or generic 500 responses.


7. DATA MODEL AND VECTOR DESIGN
--------------------------------
SQLite table emails:

id TEXT PRIMARY KEY             Gmail message ID / deduplication key
thread_id TEXT                  Gmail conversation relationship
sender, recipient, cc TEXT      Header values
subject, date, snippet TEXT     Display and retrieval metadata
label_ids TEXT                  JSON array of Gmail labels
has_attachment INTEGER          SQLite boolean (0/1)
body_text TEXT                  Parsed readable body
created_at TEXT                 SQLite insertion timestamp
category TEXT                   Local predicted category

Indexes: idx_emails_thread_id and idx_emails_category.

Vector search facts:

* Text is “Subject: {subject}\n\n{body}”.
* MiniLM emits normally 384-dimensional vectors.
* Vectors are L2-normalised. Inner product of unit vectors equals cosine
  similarity.
* IndexFlatIP is exact brute-force search: no approximation loss, but query
  cost grows linearly with mailbox size.
* JSON metadata is position-aligned with FAISS. DB/index changes require a
  rebuild; API sync does it, CLI sync does not by default.

9. UI, DESKTOP, SECURITY, AND PRIVACY
-------------------------------------
React App.jsx uses functional components, hooks, async API calls, loading/error
states, a three-pane layout, and source-card navigation. Email HTML is rendered
in an iframe sandbox without script permission. CSS owns scrolling and the
desktop layout. Electron creates a 1360×860 window and falls back from the Vite
development server to dist/index.html.

Good decisions:

* Least-privilege Gmail read-only OAuth.
* Git ignores credentials.json, token.json, local DBs, node_modules, and dist.
* Local storage/search and local_files_only models reduce cloud exposure.
* Electron has context isolation and disabled renderer Node integration.
* SQL values are parameterised.
* Summary generation is constrained to a retrieved source and has a fallback.

Risks and improvements:

* token.json and mail.db are plaintext at rest: use OS keychain/permissions and
  encrypted storage, minimise retention/logging, and offer deletion/revocation.
* Persist refreshed tokens and handle missing/bad OAuth files clearly.
* Bind only to loopback, restrict CORS/methods, and protect the local API with
  a per-launch secret in packaged use.
* Sanitize mail HTML and block remote images; sandboxing reduces script risk but
  does not eliminate phishing visuals/tracking resources.
* Use retries/backoff/rate-limit handling and non-sensitive structured logging.
* Write FAISS and metadata atomically/version them to prevent mismatch after an
  interrupted rebuild.


10. LIMITATIONS AND NEXT ENGINEERING STEPS
------------------------------------------
1. N+1 Gmail requests: list IDs then get each full email. Add pagination,
   bounded concurrency, Gmail history IDs, and incremental sync.
2. INSERT OR IGNORE makes sync idempotent but stale. Use UPSERT and Gmail
   history/internal date to update labels/read-state/body.
3. FAISS can become stale after CLI sync. Version/rebuild atomically or perform
   incremental index updates.
4. IndexFlatIP is linear. Benchmark then consider HNSW/IVF and metadata-aware
   retrieval for larger mailboxes.
5. MIME parsing returns first readable body, may include reply history, and
   only detects attachment filenames. Prefer text/plain, track parts/charset,
   strip quotes/signatures, and distinguish inline content.
6. Categorisation is heuristic, not trained. Add labelled feedback, confidence
   thresholds, Uncategorized fallback, offline precision/recall/F1, and model
   versions.
7. Keyword intent detection is ambiguous for multi-part questions. Add a tested
   grammar or constrained classifier with clarification UX.
8. Packaging needs Electron to supervise/bundle Python and models securely.
9. test_parser.py/test_cleaner.py are live Gmail smoke scripts, not CI tests.
   Add pytest fixture/mocks, FastAPI TestClient, React tests, and E2E tests.
10. Pin every imported runtime dependency and compatible Python version.


11. INTERVIEW QUESTIONS AND ANSWERS
-----------------------------------
Q: Why use SQLite and FAISS together?
A: SQLite is durable source-of-truth storage and excels at exact fields,
filters, and transactions. FAISS is purpose-built vector similarity search.
Making FAISS derived means it can be rebuilt from SQLite.

Q: Why normalise vectors with IndexFlatIP?
A: L2-normalisation makes dot product equal cosine similarity, so inner-product
search measures semantic directional similarity without vector magnitude bias.

Q: Is this really RAG?
A: It is constrained retrieval augmentation. SQLite/FAISS retrieves sources
first; most answers are formatted deterministic records. Generation only
summarises a retrieved mail, reducing hallucinated inbox facts.

Q: How does the project prevent hallucination?
A: Retrieval establishes the source, non-summary paths generate no facts,
summaries receive only selected source text, generation is deterministic, and
invalid output falls back to a source-derived excerpt.

Q: Why hybrid categorisation?
A: Rules provide explainable high-confidence handling for obvious senders and
keywords; embeddings cover the remaining messages. It is a bootstrap approach
until labelled data supports a trained, evaluated classifier.

Q: How is sync idempotent?
A: Gmail message ID is SQLite’s primary key and INSERT OR IGNORE reveals
whether it is new. Repeated syncs do not duplicate rows; the known trade-off is
that existing records are not refreshed.

Q: What is the key consistency challenge?
A: FAISS positions and JSON metadata are aligned. DB changes without rebuild
make search stale; interrupted separate writes can corrupt alignment. I would
atomically version/publish both or maintain an incremental index.

Q: How would you scale it?
A: Measure first; then batch embeddings, use HNSW/IVF approximate search,
metadata prefiltering, model/index caching, and recall@k evaluation against an
exact baseline.

Q: How do you protect mail privacy?
A: Least-privilege OAuth and local processing are the start. Production needs
encrypted local data/keychain tokens, minimal logging, safe HTML rendering,
loopback API protection, deletion/revocation controls, and explicit consent for
any cloud processing.

Q: Why FastAPI instead of renderer-to-Python calls?
A: It creates a stable/testable HTTP contract while retaining Python Gmail/ML
libraries and keeping Electron’s renderer security restrictive. Packaged use
should supervise FastAPI or replace it with a narrow IPC bridge.

Q: What tests would you add first?
A: MIME/parser and cleaner fixtures; repository idempotency/date ordering;
intent/filter/index-metadata alignment; FastAPI contracts; UI loading/error/
source navigation. Isolate OAuth as integration testing, never routine CI.

13. RUN COMMANDS
----------------
From root:

  .\.venv\Scripts\python.exe -m pip install -r requirements.txt -r requirements-api.txt
  .\.venv\Scripts\python.exe -m pip install faiss-cpu sentence-transformers transformers torch
  npm install

Run backend from src because imports use it as their module root:

  cd src
  ..\.venv\Scripts\python.exe -m uvicorn api:app --host 127.0.0.1 --port 8000

In another terminal:

  npm run dev
  $env:VITE_DEV_SERVER_URL = 'http://localhost:5173'
  npm run desktop

Useful src commands:

  ..\.venv\Scripts\python.exe main.py                 # sync; no index rebuild by default
  ..\.venv\Scripts\python.exe -m ml.build_index       # build/rebuild FAISS
  ..\.venv\Scripts\python.exe categorize_emails.py    # categorise stored email
  ..\.venv\Scripts\python.exe search_emails.py         # interactive semantic search
  ..\.venv\Scripts\python.exe rag.py                   # interactive assistant
